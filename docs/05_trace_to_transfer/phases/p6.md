# P6 — Implementation blueprint

**Status:** COMPLETE for design/documentation scope, 2026-11-04. The P6 blueprint itself is not an implementation or broad engineering authorization. A separate, narrowly scoped local/synthetic Step 1 was authorized after P7; it is tracked in the [implementation plan](../implementation/step1_event_journal_plan.md) and does not enable experiments, ARC runs, splits, or restricted data.

## Objective

Map the agreed P2 object and P3–P5 method to software components, interfaces, logs, contract tests, and resource accounting without building or running them.

## Work sequence and outcomes

1. **P6.1 — Architecture:** complete. Defined logical components and trust boundaries, data flow, lifecycle gates, common runtime/baseline interfaces, and the P3/P5 cost-vector ledger. Restricted evaluation is separate, with no feedback path into method construction/refinement.
2. **P6.2 — Event schema:** complete. Specified immutable event envelope/order and event payload references for observations, actions, predictions, transitions, candidates/skills, lifecycle, triage, failures/fallback, costs and restricted outcomes. P2/P4 contracts remain authoritative.
3. **P6.3 — Contract tests:** complete as a plan. Defined synthetic parse/interoperability, determinism/versioning, prediction-order, abstention/fallback, replay/parity, cost and isolation tests. No test code or execution.

## Deliverable

Versioned [`T2T-P6-Blueprint-v1.0.0-draft`](../p6/README.md): architecture, event-schema proposal, contract-test plan, and updated [blueprint entrypoint](../implementation_blueprint.md).

## Acceptance and boundary

P6 is complete as a **reviewable build plan**. It specifies no implementation language, database, deployment, canonical hash/ID profile, runtime/evaluator adapter, exact test framework, numeric resource caps, access/security configuration, or named engineering reviewers; these remain open and must be reviewed before implementation. Passing future contract tests would be engineering evidence only, not scientific evidence or authorization. Code, tooling, tests, experiments, benchmarks, ARC runs, split assignment, and restricted-outcome access require authorization under existing gates. The separate Step 1 authorization covers only local event validation/journaling and synthetic contract tests; no ARC or empirical activity occurred.
