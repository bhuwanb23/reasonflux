# Phase 13G preregistration — PHASE-13G-ARC-AGI-2-TRACE-TRANSFER-V1

**Status:** frozen before data retrieval and outcome analysis (2026-11-01, Asia/Kolkata). **Primary question:** does the repository's trace → invariant → skill → transfer → capability-growth pathway produce reusable, exact-fit symbolic programs with better held-out utility and lower bounded search cost on ARC-AGI-2 task IDs, without changing the core theory? This is an ARC-AGI-2 public-training-set study, not a claim that ASFT solves ARC and not a score on the official public evaluation set.

## 1. ARC validation philosophy and evidence boundary

The study treats ARC tasks as input/output demonstrations plus test inputs with exact-grid outputs. The task ID—not each grid pair—is the independent unit. It evaluates whether a compact, explicit reasoning DSL can emit honest traces, mine recurring structures, form transferable program skills, and reduce bounded program-search cost. It does not optimize for benchmark score, tune on the official evaluation split, or infer that a small DSL's successes imply general ARC competence. The current repository's synthetic grid solver is not presented as an ARC solver.

Only ARC-AGI-2 `data/training` task JSONs are analyzed. The official repository's `data/evaluation` (120 tasks), semi-private and private evaluations are excluded and never scored or used as feedback. **Transport deviation, disclosed before analysis:** while locating the training task list, a temporary upstream compressed archive that also contained evaluation blobs was downloaded. Only the archive's filename listing was queried to verify training-file count; no evaluation JSON was extracted, parsed, or scored, and the archive was deleted. The 1,000 training IDs are partitioned deterministically into 600 discovery, 200 transfer, and 200 final holdout tasks. Task IDs are ranked by `SHA256("phase13g-v1:" + id)`; first 600 are discovery, next 200 transfer, final 200 holdout. IDs, counts, and file hashes are saved before analysis. The fixed task split is disjoint. A pre-run schema audit decoded all 1,000 training JSONs (including eventual holdout) only to check grid rectangularity and color range; it did not compare inputs to outputs, assign families, run a solver, or score outcomes. In the analytic runner, discovery outcomes build the library, transfer outcomes validate candidate skills, and holdout task JSONs are loaded only after the library/arms/config are frozen. The independent final estimate is therefore the 200-task holdout only. No Phase 13C–13F evidence is pooled or edited.

## 2. Taxonomy and DSL coverage

ARC-AGI-2 supplies no authoritative task-family annotations. We will not create them by subjective labeling. A fixed, bounded program inventory is used: identity, horizontal/vertical reflection, 90/180/270-degree rotation, transpose, anti-transpose, constant non-wrapping translation, and bijective color remapping. A program is recognized only if it exactly fits every demonstration pair. Translation parameters use a deterministic rare-color anchor search (up to 16 source anchors) followed by full-grid exact replay; this can create false negatives but not false-positive fits. Otherwise the task is `unsupported_v1`, not a forced family label.

The requested concepts—reflection, rotation, translation, counting, grouping, object detection, pattern completion, symmetry—are reported in the taxonomy/coverage table. Reflection, rotation, and translation receive direct program labels where exact fit supports them. Symmetry is recorded as an independently computed input/output property, not conflated with a solved rule. Counting, grouping, object detection, and pattern completion are marked not operationalized in v1 unless the fixed program library directly supports them (it does not). Their task prevalence and success are not guessed. `Other/unclassified` remains a first-class category. Dataset taxonomy coverage means the share of tasks with an exact-fit supported rule; it is not an estimate of ARC's semantic family prevalence.

## 3. Trace quality and stability — EXP-ARC-07

For each supported discovery task, record four typed steps: `validate_grid_schema`, `enumerate_candidate_programs`, `apply_program`, and `verify_demonstrations`. The trace includes task ID, demo count, program ID, per-demo exact-fit flags, and test-output access status; it contains no invented intermediate reasoning. Trace success means exact fit on all demonstrations, verified independently by replay. Schema completeness and exact-fit fidelity are the primary trace-quality measures. Stability is the fraction of 10 fixed permutations of demonstration-pair order (seed 1307) returning the same selected program; report both overall and by program. Ambiguous tasks with multiple fitting programs are retained and the fixed program-order tie-break is disclosed.

## 4. Invariants and IS–transfer relation — EXP-ARC-10

Run the existing repository `TraceMiner`/invariant candidate pipeline on successful discovery traces only, frozen with minimum frequency 5, minimum cross-trace 5, minimum core length 1, maximum fragment length 4, and successful-trace bias. Candidate discovery cannot see transfer/holdout outputs. The repository definition `IS = frequency × consistency × generality` is retained. Here, generality is explicitly limited to the number of observed program/task buckets in this v1 DSL; this limitation is reported. Invariant precision is the proportion of promoted candidates that have independent exact-fit replay on all source demos and at least one distinct transfer task. Report candidate count, accepted/rejected reasons, recurrence, stability, and transfer outcomes. The IS–transfer relationship uses holdout task-level results for final descriptive association; it is not a causal estimate and will be shown with uncertainty and denominators.

## 5. Skills, SCV, and utility — EXP-ARC-13

An invariant may propose a skill only after at least five distinct discovery task IDs support its exact program signature. Transfer split is used once to validate proposed skills and obtain measured reuse/transfer evidence; no transfer label tunes the DSL, support threshold, or candidate ordering. The skill's SCV uses the existing `SkillCandidate` definition `reuse × abstraction_gain × transfer_score − creation_cost`; reuse is `min(1, successful transfer task IDs / SkillConfig.reuse_norm=10)`, abstraction gain is the mean positive B1 candidate-trial saving divided by 10 DSL programs, transfer score is successes / exact-demo-fit applicable attempts, and creation cost is the existing default 0.1. Promotion additionally requires at least three applicable transfer tasks and the unmodified repository `qualify_candidate` gate. Only observed transfer evidence is used, not a prior masquerading as measured evidence. Report both promoted and rejected candidates, full SCV components, successful/failed reuses, utility, and whether skills actually execute on distinct task IDs. Skill counts alone do not establish emergence.

## 6. Transfer — EXP-ARC-15

Near transfer is reuse of the same exact-fit skill on a distinct task ID. Cross-family transfer is estimated only when independently observed structural buckets differ; because ARC-AGI-2 has no semantic family labels, the report may state that cross-semantic-family transfer is unidentifiable. Structural transfer is exact generalization to test inputs with held-out dimensions/colors/object counts, categorized by fixed measurable grid properties after the predictor is frozen. All results are split-specific. The primary endpoint is exact task accuracy: every test output grid in the task must match exactly. Report task counts, pair counts, accuracy, and failure type; unsupported-v1 tasks remain in overall denominators and are failures for the bounded system.

## 7. Search cost and B1–B4

Per task, each arm can evaluate at most three distinct DSL programs against demonstrations. A candidate counts as a trial even when it fails. All arms use the same DSL, exact-fit check, test inputs, and budget. B1 is fixed-order no-learning search. B2 is an episodic memory comparator: order candidates by nearest discovery-task grid statistics, no invariant abstraction; any retrieved program must still pass exact demo validation. B3 uses a task-ID-keyed random permutation of the same eligible operator pool. B4 compresses only exact repeated full trace signatures; it is a compression-only proxy, not canonical DreamCoder. ASFT mines recurrent trace structures, converts qualifying invariants into skills after transfer validation, then orders skills by discovery support before remaining fixed-order candidates. All arms require exact demonstration validation, and no arm has an unbounded fallback. Candidate trials and exact task accuracy are both reported. This is bounded symbolic search cost, not human-equivalent reasoning time or FLOPs.

## 8. Capability growth and IG — EXP-ARC-17

The capability unit is a validated reusable transform skill. A capability group requires at least two independently validated skills and successful transfer evidence; a one-skill library does not become a capability by relabeling. Report capability emergence, skill and program-family coverage, task coverage, and growth by cumulative discovery prefix (fixed task-hash order). Compute CGR/IG only through the existing Phase 13E pathway and frozen weights. For the existing coverage-growth input, use distinct successfully transferred bounded-program families divided by the six fixed program-family labels in the DSL; this is not semantic ARC-family coverage. If a required validated capability or component is absent, retain `unavailable` rather than substituting a new ARC-specific formula. IG is a repository-derived proxy in this bounded task setting—not a measure of general intelligence. Record capability-count illusions, fragmentation, negative transfers, and saturation.

## 9. Statistical plan and failure analysis

The independent unit is task ID. Primary contrasts are paired ASFT-minus-B1/B2/B3/B4 differences on the same 200 holdout tasks for exact task accuracy and candidate trials. Use a paired task-ID bootstrap (10,000 resamples, seed 1307), two-sided 95% percentile intervals. Report point estimates and denominators; no pseudo-replication of input/output pairs. No post-result threshold, split, operator, metric, baseline, or exclusion changes. Null, adverse, missing, and unsupported findings stay visible. Failure analysis distinguishes: malformed/unavailable data; no DSL rule fits demos; demo ambiguity; demo-fit but test mismatch; budget cutoff; unstable trace; skill negative transfer; capability/IG unavailable. No out-of-DSL task is described as an ARC model failure outside the defined bounded system.

## 10. Evidence package

Produce exactly six main figures and six main tables: (1) task taxonomy/DSL coverage; (2) trace schema quality and permutation stability; (3) invariant strength versus transfer with uncertainty; (4) skill emergence/SCV/reuse utility; (5) transfer and exact task accuracy by split/structural category; (6) candidate-trial cost plus capability growth/IG. Tables cover split integrity and dataset hashes; taxonomy/operator coverage; trace validity/stability; invariant/skill candidate lifecycle; B1–B4 transfer/accuracy/cost contrasts; capability/IG, failures, and unavailable metrics. Machine-readable task-level CSV/JSON and run manifest accompany them. All artifacts disclose the archive-transport deviation; no official evaluation task JSON was extracted, parsed, scored, or used as feedback.
